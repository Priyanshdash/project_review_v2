# CyberSentinel-LLM: Project Implementation Specification

## 1. Project Objective

Implement a research-based project titled **“A Large Language Model-Driven Autonomous Framework for Intelligent Cyber Threat Detection and Response”**, using the supplied research paper as the primary technical reference.

The objective is to build a functional, modular, and experimentally evaluated cybersecurity framework that combines traditional machine learning classifiers, local Large Language Model inference, coordinated detection and response components, and a dashboard for monitoring and analysis.

The research paper is the source of truth for the proposed architecture, methodology, and claims. Read it carefully before finalizing the design. Identify which components are explicitly described by the paper and which components must be implemented as practical adaptations.

Do not claim that an implementation reproduces a paper's method exactly unless the paper and the implementation support that claim.

## 2. Critical Project Constraints

1. Use the existing local LLaMA 3 8B installation for inference. Inspect its runtime and loading requirements before modifying anything.
2. **Do not fine-tune, retrain, or otherwise modify the LLaMA model weights in this phase.** Fine-tuning belongs to a separate future phase.
3. Implement both traditional ML classification and LLM-based threat analysis.
4. Evaluate the classifier and LLM separately and compare their results where a valid comparison is possible.
5. Include a combined classifier-plus-LLM workflow and evaluate it separately.
6. Create only files that have a clear implementation purpose. The suggested file structure is not a mandatory checklist.
7. Never create empty placeholder files merely to make the project appear complete.
8. Do not fabricate datasets, experimental results, evaluation metrics, successful tests, or model capabilities.
9. Prefer an end-to-end working implementation over a large collection of incomplete modules.
10. Maintain `progress.txt` throughout implementation so work can be resumed in a new session.

## 3. Research Paper Analysis

Before coding:

- Extract the paper's problem statement, research objectives, proposed architecture, methodology, datasets, model types, agent roles, evaluation metrics, and reported findings.
- Identify the framework's inputs, intermediate representations, outputs, and decision flow.
- Record the algorithms and components explicitly required by the paper.
- Identify components that are underspecified, unavailable, impractical on the current hardware, or dependent on unavailable data.
- Separate the paper's reported results from results generated by this implementation.
- Create an implementation mapping that links each important paper requirement to the planned component, implementation status, and verification method.

If a proposed feature is not supported by the paper, do not silently attribute it to the paper. Mark it as an extension or practical adaptation.

## 4. System Architecture

Implement the following high-level pipeline, adapting it to the paper's actual methodology:

Security data
→ Data preprocessing and feature extraction
→ ML-based threat classification
→ LLM-based contextual analysis
→ Evidence-based response recommendations
→ Combined results and evaluation
→ Dashboard and reports

The framework should be modular, maintainable, and testable.

Potential components include:

- Dataset ingestion and validation
- Data cleaning and feature engineering
- Model training and evaluation
- Threat classification
- Local LLaMA inference
- Detection, classification, response, and forensic agent logic, where justified by the paper
- Response orchestration, where justified by the paper
- Dashboard and reporting
- Logging, configuration, and tests

Use a simple architecture when possible. Do not split every function or algorithm into its own file unless that separation provides a genuine benefit.

## 5. Dataset Handling

Investigate the availability, format, licensing, compatibility, and resource requirements of the datasets discussed in the paper.

Potential benchmarks previously identified for investigation include:

- HDFS system logs
- BGL system logs
- CICIDS2017 network traffic
- NSL-KDD intrusion detection data

These datasets serve different purposes and must not automatically be treated as interchangeable. HDFS and BGL are log-oriented benchmarks, while CICIDS2017 and NSL-KDD are network intrusion detection datasets.

Use only the datasets that can be obtained and processed appropriately. Follow the paper's actual dataset requirements where specified.

For each dataset:

- Verify that the files are readable and contain the expected fields.
- Inspect missing values, duplicates, class distributions, and data types.
- Document preprocessing and feature selection.
- Encode categorical variables and handle numerical features appropriately.
- Prevent data leakage between training, validation, and testing.
- Use stratified splitting where suitable.
- Use chronological or group-aware splitting when required by the data structure.
- Address class imbalance where justified.
- Record the dataset version, source, split configuration, and random seed.

Do not silently merge incompatible datasets or assume that identically named labels have identical meanings.

If a dataset is unavailable, document the limitation and continue with a valid available dataset where possible.

## 6. Traditional Machine Learning Classification

Build a reproducible classification pipeline using the algorithms required by the paper. If the paper does not specify a complete model list, consider the following candidates where appropriate:

- Logistic Regression
- Decision Tree
- Random Forest
- Extra Trees
- Gradient Boosting
- HistGradientBoosting
- XGBoost, if available and compatible
- Support Vector Machine
- K-Nearest Neighbors
- Naive Bayes
- Multilayer Perceptron

Do not implement every candidate blindly. Prioritize the paper's required algorithms and select additional baselines based on dataset characteristics, computational cost, and experimental value.

Requirements:

- Use suitable preprocessing pipelines.
- Fit preprocessing steps on training data only.
- Tune hyperparameters using training/validation data, not the final test set.
- Save trained models and the associated preprocessing configuration.
- Record training duration and inference latency.
- Support reproducible evaluation.
- Report errors and failed experiments honestly.

### Classification metrics

Report applicable metrics, including:

- Accuracy
- Precision
- Recall
- F1-score
- Macro-F1 and weighted-F1
- Confusion matrix
- ROC-AUC and precision-recall AUC when appropriate
- Per-class performance for imbalanced datasets
- Training time and inference latency

Use the metrics required by the paper in addition to relevant supplementary metrics.

Identify the best classifier using a declared validation criterion. Do not choose a model based on final test-set performance and then present the same test set as an unbiased evaluation.

Generate comparison tables, plots, and machine-readable prediction files from actual evaluation runs.

## 7. Local LLaMA 3 8B Inference

Use the already-installed local LLaMA 3 8B model for inference only.

Before implementation, inspect the existing model location, inference runtime, dependencies, available memory, and supported quantization or loading options.

Do not download another model unnecessarily. Do not expose model credentials, tokens, or private paths in public logs.

Design prompts that request structured, evidence-based cybersecurity analysis. Depending on the input and model capabilities, the LLM may produce:

- A threat or event explanation
- A predicted threat category
- A severity assessment
- Supporting evidence from the supplied input
- Defensive recommendations
- Potential indicators of compromise, when supported by the input
- A forensic summary
- A structured JSON response

The LLM must distinguish observed evidence from inference and uncertainty. It must not invent log entries, network events, indicators, or facts absent from the input.

Validate generated JSON, handle malformed outputs, use bounded input sizes, and implement suitable error handling.

Do not assume the LLM can access external systems, execute actions, or inspect files unless those capabilities are explicitly implemented.

### LLM evaluation

Evaluate the LLM on a held-out set of samples for which reliable ground-truth labels are available.

Where the task supports classification, evaluate the predicted labels against ground truth using applicable metrics such as accuracy, precision, recall, macro-F1, and weighted-F1.

For free-form threat analysis, additionally assess:

- Factual consistency with the input
- Evidence traceability
- Correctness of the explanation
- Usefulness and safety of recommendations
- Structured-output validity
- Invalid or incomplete output rate
- Inference latency

Use human review, documented rules, or another clearly described evaluation method for qualitative criteria. Do not represent subjective assessments as objective ground truth.

Report the inference configuration, prompt version, model identifier, sample count, and any relevant decoding settings.

**Fine-tuning is explicitly out of scope for this phase.** Do not train the LLaMA model, generate fine-tuned checkpoints, or claim that its weights have been adapted to the project dataset.

## 8. Fair Comparative Evaluation: ML vs. LLM vs. Combined System

This is a mandatory project requirement.

Evaluate three distinct configurations wherever the data and methodology support them:

### A. Classifier-only

The selected ML classifier predicts the threat class from the appropriate features.

### B. LLM-only

The local LLaMA model analyzes the relevant input and produces a threat prediction or analysis without using the ML classifier's predicted class as an input.

### C. Classifier + LLM

The ML classifier and LLM work together. Define their responsibilities clearly, such as using classifier predictions and supporting evidence to guide LLM explanation and response recommendations.

If the system combines predictions algorithmically, document the fusion method. Do not claim that the combined system improves classification performance unless measured results demonstrate that improvement.

### Fairness requirements

- Evaluate configurations on comparable held-out samples wherever possible.
- Establish consistent label mappings and a common evaluation protocol.
- Clearly distinguish structured classification outputs from free-form LLM analysis.
- Do not compare incompatible label spaces without explaining the limitation.
- Do not provide the LLM with ground-truth labels during inference.
- Avoid test-set leakage through prompt construction, threshold selection, or model selection.
- Report missing predictions, failed requests, and invalid outputs.
- Report both successful-output metrics and overall system reliability where applicable.

### Required comparison outputs

Produce a comparison table containing the applicable metrics for all three configurations.

Include:

- Accuracy, precision, recall, macro-F1, and weighted-F1 for comparable classification tasks
- Confusion matrices where applicable
- Per-class performance
- LLM inference latency
- Classifier training and inference time
- Combined pipeline latency
- LLM output validity and failure rates
- Qualitative analysis quality for LLM outputs
- Resource consumption where practical

Save the underlying predictions, ground-truth labels, metrics, configuration, and plots.

If an evaluation cannot be performed fairly, explain why and report the results separately rather than manufacturing a direct comparison.

## 9. Agent Architecture and Response Orchestration

Inspect the research paper to determine which agents and coordination mechanisms it actually requires.

Potential agent responsibilities include:

1. **Detection agent:** identifies suspicious events using available models and evidence.
2. **Classification agent:** consolidates or interprets predicted threat categories.
3. **Response agent:** proposes appropriate defensive actions.
4. **Forensic agent:** produces an evidence-grounded incident summary.

Implement separate agents only when their responsibilities and interfaces are meaningful. Shared functions may be implemented in reusable modules.

If the paper requires reinforcement learning or PPO-based response orchestration:

- Determine the state, action, reward, transition, and termination definitions from the paper or document the adaptation.
- Implement the environment and reward logic explicitly.
- Evaluate the approach against an appropriate baseline where feasible.
- Do not describe a rule-based approximation as trained PPO.
- Do not fabricate training episodes, reward curves, or convergence claims.

If PPO is not essential to the minimum working system or cannot be implemented and evaluated within available resources, document it as deferred rather than presenting it as completed.

## 10. Safe Defensive Response

The framework is intended for defensive cybersecurity research.

Initially, responses must be simulated or presented as recommendations. Examples include:

- Recommend investigating a suspicious source.
- Suggest reviewing access logs.
- Recommend isolating a potentially compromised endpoint.
- Suggest updating firewall rules after human review.
- Recommend preserving relevant forensic evidence.

Do not automatically block users, modify firewall configurations, terminate processes, delete files, or execute other potentially disruptive actions.

Any future live-response capability must be isolated, explicitly authorized, tested, logged, and subject to appropriate safeguards.

The LLM must not independently execute actions based solely on generated text.

## 11. Dashboard and Reporting

Build a functional dashboard, preferably using Streamlit if appropriate for the environment.

The dashboard should display actual outputs produced by the implemented system, including:

- Dataset and experiment information
- Classifier predictions and confidence scores where supported
- Model comparison metrics
- LLM explanations and recommendations
- Combined pipeline outputs
- Confusion matrices and performance charts
- Detection history or event summaries
- Response recommendations and their status
- Errors, failed predictions, and inference latency

Allow a user to submit a supported sample or select an available test record and inspect the results.

The dashboard must call the actual backend implementation. Do not substitute hardcoded demonstration results for model predictions.

Clearly distinguish demonstration data from real experimental results.

## 16. Implementation Phases

### Phase 1: Inspect and plan
Read the paper, inspect the existing project, verify the local LLaMA installation, inspect hardware and datasets, and establish the implementation plan.

### Phase 2: Minimum working pipeline
Implement dataset loading, preprocessing, one appropriate baseline classifier, evaluation, and local LLaMA inference.

### Phase 3: Comparative experiments
Add the required classifier baselines and conduct classifier-only, LLM-only, and combined-system evaluations where valid.

### Phase 4: Integration and dashboard
Connect the backend components and expose real predictions, metrics, explanations, and recommendations in the dashboard.

### Phase 5: Research-specific components
Implement additional agents, temporal models, reinforcement learning, or other architecture components when required by the paper and supported by the environment.

### Phase 6: Verification and documentation
Run tests, verify results, document limitations, and update the project status.

Do not skip essential validation merely to reach a later phase.

## 17. Progress Persistence

Maintain `progress.txt` as the authoritative implementation handoff document.

After each meaningful milestone, update it with:

- Current phase and overall status
- Components completed
- Files created or modified
- Commands executed
- Test and experiment results
- Dataset availability and limitations
- Model paths or configuration references, without exposing secrets
- Errors and unresolved problems
- Important architecture decisions
- Work deferred to a later phase
- Exact next actions in priority order

Record the latest verified state, not the state that is merely intended.

When starting a new session, read `progress.txt` and inspect the actual files before continuing.

Never assume that a previous agent completed a task merely because the progress file says it should have been completed; verify important claims against the implementation.

## 18. Completion Criteria

The project is complete for the current phase when:

- The implemented architecture is documented and traceable to the paper.
- The available dataset pipeline executes successfully.
- At least one valid ML classifier is trained and evaluated.
- Local LLaMA 3 8B inference works without fine-tuning.
- The classifier and LLM outputs are available for inspection.
- A combined workflow is implemented and evaluated where feasible.
- The comparative evaluation reports real results and limitations.
- The dashboard displays actual backend outputs.
- Relevant tests have been run and their results documented.
- Setup instructions are reproducible to the extent possible.
- `progress.txt` accurately records the final status and remaining work.

Do not claim completion of deferred, unavailable, untested, or partially implemented components.

**Primary principle:** Build a working, evidence-based, reproducible cybersecurity research system. Prioritize correctness, measurable results, honest reporting, and resumable progress over unnecessary files or superficial feature counts.
